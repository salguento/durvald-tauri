# Durvald technical documentation

> Version 0.1.0 · Desktop application under development · Updated July 2026

## Overview

Durvald is a local-first music player. Its interface is built with SolidJS and TypeScript; the native process uses Tauri and Rust to access the filesystem, read metadata, persist the library and play audio. When opened in a regular browser, the project serves a static product showcase and does not access local files.

## Architecture

```text
SolidJS UI
  ├─ pages, components and reactive stores
  ├─ audio/library hooks
  └─ Tauri invoke + event listeners
                │
                ▼
Tauri command boundary
  ├─ audio player (Kira)
  ├─ metadata scanner (Lofty)
  ├─ library and session persistence (SQLite)
  └─ Last.fm client + secure credential storage
                │
                ▼
Local filesystem, OS credential store and Last.fm API
```

The frontend calls Rust commands through `invoke`. The backend publishes events such as `progress-update` and `song-changed`; reactive stores update the queue, current track and interface. Blocking SQLite operations use a connection pool and dedicated tasks, while playback, progress updates and HTTP calls run through Tokio.

## Technology stack

| Layer | Technology | Responsibility |
| --- | --- | --- |
| Interface | SolidJS, TypeScript, Tailwind CSS | Routes, components and reactive state |
| Desktop | Tauri 2 | Native window, permissions and IPC bridge |
| Core | Rust, Tokio | Commands, concurrency and asynchronous tasks |
| Audio | Kira | Streaming, pause, seek, volume and queue |
| Metadata | Lofty | Tags, duration, bitrate and embedded artwork |
| Data | SQLite, rusqlite, r2d2 | Library, playlists, history, queue and session |
| Integration | reqwest, Last.fm API | Authentication, now playing and scrobbling |
| Secrets | Keyring / AES-256-GCM | Platform-specific credential storage |

## Main flows

### Library indexing

1. The user selects one or more folders during onboarding.
2. The backend walks supported files and Lofty extracts tags and technical properties.
3. Artists, releases and tracks are normalized and stored in SQLite.
4. `mirrorDB` loads the records into SolidJS stores.

The player enables MP3, OGG, FLAC and WAV formats.

### Playback and queue

`AudioPlayer` keeps the current track, a `VecDeque` queue and an in-memory history. Queue changes are also persisted in SQLite. An asynchronous loop detects the end of a track, starts the next item, saves the queue and emits `song-changed`. Progress is emitted separately to the interface.

### Session

A single session row stores the current track, position, volume, shuffle, repeat mode, queue snapshot, queue position and source context. Persisting it allows the application to resume state after closing.

### Last.fm

The integration implements token authentication, now-playing updates and scrobbling. A global limiter enforces a minimum one-second interval between requests. Scrobbles that fail because the network is unavailable enter a `localStorage` queue and are retried after connectivity returns.

## Data and security

- Library, queue, playlists, settings, history and last session are stored in the local `music.db3` file.
- On macOS, Last.fm secrets are stored in Keychain through the `keyring` crate.
- On Windows and Linux, secrets are encrypted with AES-256-GCM and bound to the local machine/user identity.
- API key and username, treated as non-secret data, live in the application data directory.
- The main capability limits access to window operations, dialogs, filesystem and URL opening.
- Durvald does not upload audio files to external services.

## Requirements

- Bun 1.x
- Stable Rust and Cargo
- Tauri 2 system dependencies for the target operating system
- Last.fm application credentials, only when scrobbling is enabled

## Development

```sh
bun install
bun run dev          # web showcase
bun run tauri dev    # complete desktop application
```

## Validation and build

```sh
bun run check
bun run build
cargo check --manifest-path src-tauri/Cargo.toml
bun run tauri build
```

`bun run build` runs TypeScript validation before Vite. Web output is written to `dist/`; desktop installers are generated by Tauri for the current build platform.

## Runtime environments

The bootstrap checks for `__TAURI_INTERNALS__`. Under Tauri it loads the complete application and signals that the main window is ready. In a standard browser it loads only the showcase as a separate chunk and does not execute native commands.

## Current limitations

- The project is at version 0.1.0 and does not yet include an automated test suite.
- Library quality depends on consistent metadata in audio files.
- The database currently creates tables incrementally at startup without a formal migration framework.
- Last.fm requires users to provide their own application credentials.
